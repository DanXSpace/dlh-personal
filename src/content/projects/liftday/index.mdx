## The idea

I spend a fair amount of time in the gym, and I wanted a workout tracker that complemented the training experience rather than getting in the way of it.

You should know what you're training today, be able to record your performance quickly and understand whether you're making progress over time.

LiftDay is my attempt to bring those ideas together.

## The approach

My focus is on reducing friction during workouts, making training data meaningful and creating an interface that feels at home on iOS.

Rather than building around an overwhelming collection of features, I want the core experience to be simple enough to use consistently.

I'm developing the application natively using Swift and SwiftUI, giving me an opportunity to explore Apple's development ecosystem while building something I can use in my own life.

## How it's built

LiftDay separates its core training logic from the iOS application itself.

WorkoutCore is a standalone Swift package responsible for training statistics, progression rules, workout plan generation and the validation of AI-generated output. The iOS application handles presentation, persistence and platform integrations.

Keeping WorkoutCore independent of the interface and database allows me to test the application's core behavior without launching an iOS simulator. It also gives the training logic a clear boundary, independent of how the application looks or stores its data.

SwiftData handles local persistence. Body weight is managed differently: Apple Health remains the source of truth for weigh-ins, avoiding duplicate records and unnecessary synchronization logic.

## Decisions worth explaining

### Swift does the math. The model does the language.

Every weight recommendation, rep target and progression decision comes from deterministic Swift code.

The language model has a narrower responsibility: interpreting natural language and communicating information generated by the application.

I wanted the flexibility of a language model without introducing its unpredictability into decisions that affect someone's training.

### Intelligence without the cloud.

LiftDay's AI features use Apple's Foundation Models framework, running directly on supported devices.

This eliminates the need for a cloud inference service, avoids per-request API costs and allows supported AI features to work offline. User input processed by these features stays on the device.

Every AI-powered feature also has a non-AI fallback. On devices without Apple Intelligence, for example, the weekly training review presents a straightforward statistical summary instead of a generated narrative.

AI enhances the experience, but it isn't a requirement for using the application.

### The model reads. Swift decides.

The AI workout template builder went through an important architectural change during development.

My initial approach was to have the language model generate an entire training plan. Testing with the real on-device model exposed several problems: incorrect training frequencies, equipment that contradicted user constraints and inconsistent adherence to instructions.

Rather than continuing to refine the prompt, I reconsidered the responsibility I was giving the model.

The current implementation separates interpretation from execution. The model extracts the user's intent — their goals, available equipment, training frequency and other preferences — and provides supporting excerpts from the original request.

Swift validates those excerpts against the input, distinguishes supported information from assumptions and constructs the workout plan using deterministic rules.

In my testing, this narrower responsibility produced more reliable results.

The most useful lesson wasn't how to write a better prompt. It was recognizing that changing the system's boundaries could address the problem more effectively than asking the model to behave better.

### One internal representation.

LiftDay stores training weights in pounds and converts them into the user's preferred unit for display.

Using a consistent internal representation prevents calculations, comparisons and progression rules from operating on incompatible units.

It's a small architectural decision that removes an entire category of potential errors.

## Testing and validation

WorkoutCore has automated tests covering training statistics, progression rules, workout plan generation and AI-output validation. These tests run independently of the iOS simulator.

Changes to AI prompts undergo a separate evaluation on a Mac with Apple Intelligence. Because the underlying model can change with operating system updates, I treat prompt behavior as something that requires ongoing validation rather than a fixed dependency.

Interface checks are done by hand in the simulator, on the smallest supported iPhone, at the largest accessibility text size and on the iPhone Duo's outer display. The Duo's inner display hasn't been checked yet.

## How I build

LiftDay is also an experiment in structured, AI-assisted software engineering.

Development is organized around narrowly scoped tickets and a separation of responsibilities between coding agents. One coordinates the work, another implements an individual ticket in an isolated Git worktree, and a third independently reviews the implementation without modification privileges.

The goal is to make development faster without sacrificing review, testing or accountability.

I'm interested not just in what AI can build, but in how engineering workflows need to evolve to make AI-assisted development dependable.

## Current status

LiftDay is preparing for a TestFlight beta.

My initial release criterion is simple: someone other than me should be able to install the application, complete a month of training and do so without assistance or data loss.

The next milestone is validating that experience through real-world use.
